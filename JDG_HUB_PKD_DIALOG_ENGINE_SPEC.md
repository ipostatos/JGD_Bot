# JDG HUB — диалоговый подбор PKD 2025

## Техническая спецификация, архитектурное решение и инструкция для реализации

**Статус:** proposed architecture  
**Назначение документа:** дать разработчику или coding-agent (в том числе Claude) достаточный контекст, чтобы реализовать функцию корректно, не сводя задачу к очередному расширению словаря синонимов.  
**Основание:** текущий поиск JDG HUB на базе официального текста PKD 2025, BM25 и русскоязычного словаря профессий; отчёт от 23 июля 2026 года по коммиту `f788f64`.  
**Ключевая мысль:** PKD классифицирует **экономическую деятельность**, а не профессию человека. Поэтому запрос «я сварщик» или «я дизайнер» является только начальной подсказкой, но не достаточным основанием для окончательного кода.

---

# 1. Итоговое архитектурное решение

Реализовать функцию как **гибридный диалоговый классификатор**, состоящий из пяти независимых слоёв:

1. **Официальный корпус PKD 2025** — единственный источник истины по кодам, названиям, включениям, исключениям, секциям и переходам PKD 2007 → PKD 2025.
2. **Русскоязычный слой понимания запроса** — словарь профессий, разговорных формулировок, транслитераций и типичных ошибок.
3. **Поисковый слой кандидатов** — BM25/полнотекстовый поиск плюс управляемые boosts и отрицательные сигналы.
4. **Детерминированный диалоговый rule engine** — задаёт уточняющие вопросы и применяет ответы к кандидатам.
5. **LLM-слой** — извлекает структурированные факты из свободного текста, выбирает понятную формулировку вопроса и объясняет результат. LLM **не имеет права самостоятельно придумывать или назначать код PKD**.

## Почему именно гибридная схема

### Почему недостаточно только словаря

Плоский словарь хорошо отвечает на вопрос «какие коды обычно связаны с этими словами», но не отвечает на вопрос «какую именно деятельность ведёт пользователь».

Пример:

- «сборка мебели» может означать монтаж отдельно стоящей мебели;
- «монтаж кухни» может означать встроенную мебель как часть строительного объекта;
- «мебельщик» может производить новую мебель;
- тот же человек может ещё ремонтировать мебель и продавать готовые изделия.

Одно ключевое слово не кодирует бизнес-модель, объект работы, результат услуги и роль предпринимателя в сделке.

### Почему недостаточно только LLM

LLM полезна для языка, но ненадёжна как нормативный классификатор:

- может смешать PKD 2007 и PKD 2025;
- может придумать несуществующий код;
- может уверенно выбрать семантически похожий, но юридически неверный подкласс;
- её ответ сложно регрессионно тестировать;
- изменение модели или промпта может незаметно изменить результаты.

Поэтому LLM должна возвращать только заранее определённую структуру фактов, например:

```json
{
  "activity_family": "furniture",
  "actions": ["installation"],
  "object": "built_in_kitchen",
  "sells_own_goods": false,
  "acts_as_intermediary": false,
  "confidence": 0.88,
  "unknown_fields": ["manufactures_goods"]
}
```

Код выбирает только rule engine из официального каталога.

### Почему недостаточно только embeddings

Векторная близость хорошо находит семантически похожий текст, но PKD содержит много соседних кодов, различающихся коротким юридически значимым условием:

- производство против ремонта;
- собственная продажа против посредничества;
- встроенный объект против отдельно стоящего;
- разовый кейтеринг против регулярного;
- уход за домашними животными против обслуживания животноводства.

Embeddings допустимы как дополнительный recall-канал, но не должны самостоятельно определять финальный ranking.

### Почему rule engine лучше большого дерева, полностью написанного вручную

Жёстко прошитое дерево быстро становится непроверяемым. Вместо одного гигантского `if/else` нужно хранить:

- признаки деятельности;
- правила совместимости кода с признаками;
- вопросы, которые получают недостающие признаки;
- причины включения и исключения кандидатов.

Такое представление можно тестировать, версионировать и расширять отрасль за отраслью.

# 2. Нормативные ограничения, которые архитектура обязана учитывать

## 2.1. Пользователь сам классифицирует свою деятельность

Официальный подход GUS заключается в том, что субъект самостоятельно классифицирует проводимую деятельность. При сомнениях он может обратиться в Ośrodek Klasyfikacji i Nomenklatur Urzędu Statystycznego w Łodzi.

### Следствие для продукта

JDG HUB не должен писать:

> Ваш правильный код — 43.32.Z.

Корректная формулировка:

> На основании вашего описания наиболее подходящим выглядит 43.32.Z. Проверьте официальный объём кода и исключения. При нестандартной или спорной деятельности можно запросить классификационную информацию GUS.

Это не просто disclaimer. Это правильная модель ответственности продукта.

## 2.2. Для классификации нужен точный предмет деятельности

Официальный классификационный центр требует описывать одну деятельность и, для сложной услуги, указывать действие, которое придаёт ей основной характер.

### Следствие для продукта

Функция не должна пытаться решить всё по фразе «ремонт квартир» или «работаю в интернете». Она обязана:

1. выделить отдельные деятельности;
2. классифицировать каждую отдельно;
3. затем предложить главный и дополнительные коды.

## 2.3. Главный код определяется не названием профессии

Деятельность преобладающая определяется по наибольшему вкладу соответствующего показателя. В практическом интерфейсе для JDG разумно спрашивать ожидаемую долю дохода, времени или объёма заказов, но не выдавать эти показатели за полное юридическое определение добавленной стоимости.

### Следствие для продукта

Функция должна разделять две задачи:

- **какой код описывает каждую деятельность**;
- **какой из найденных кодов выбрать главным**.

Это разные этапы. Нельзя выбирать главный код только потому, что он получил самый высокий поисковый score.

## 2.4. Один субъект может вести несколько видов деятельности

CEIDG допускает один код основной деятельности и дополнительные коды для реально выполняемых направлений.

### Следствие для продукта

Итогом должен быть не всегда один код, а пакет:

- `primary_candidate`;
- `additional_candidates`;
- `not_recommended`;
- `needs_verification`.

## 2.5. PKD не определяет автоматически ставку ryczałtu

PKD описывает деятельность субъекта. Налоговая ставка часто зависит от фактически оказываемой услуги и её классификации PKWiU, а также от условий закона.

### Следствие для продукта

Нельзя выводить ставку ryczałtu из PKD как достоверный факт. Допустима отдельная функция:

> Для оценки ставки понадобится описание конкретной услуги и анализ PKWiU. PKD недостаточно.

# 3. Цель функции

## 3.1. Пользовательская цель

Человек описывает свою работу обычным русским, польским или смешанным языком и получает:

1. список отдельных видов деятельности, которые сервис распознал;
2. максимум 1–3 уточняющих вопроса для каждой неоднозначной деятельности;
3. наиболее подходящий код PKD 2025 для каждого направления;
4. предложение главного и дополнительных кодов;
5. понятное объяснение, почему код подходит;
6. объяснение, почему похожие коды не подходят;
7. предупреждение о недостаточности данных или регулируемой деятельности;
8. официальный текст GUS без генеративного пересказа вместо оригинала.

## 3.2. Техническая цель

Минимизировать две ошибки:

- **confident wrong answer** — уверенный неправильный ответ;
- **false certainty** — ситуация, когда система скрывает неоднозначность.

Пустой ответ менее опасен, чем уверенно неправильный код. Поэтому функция должна уметь остановиться и сказать `needs_clarification` или `needs_official_interpretation`.

## 3.3. Что не входит в первую версию

- автоматическая подача изменений в CEIDG;
- юридически обязательная классификационная интерпретация;
- автоматическое определение ставки ryczałtu;
- полный compliance-анализ всех лицензий Польши;
- универсальный LLM-агент без ограниченного набора схем и правил;
- автоматическая классификация без подтверждения пользователя.

# 4. Целевой пользовательский сценарий

## Шаг 1. Свободное описание

Вместо поля «профессия» использовать вопрос:

> Чем именно вы зарабатываете или планируете зарабатывать? Опишите, что делаете, для кого, с каким результатом и продаёте ли собственный товар.

Под полем показать короткий пример:

> Например: «Изготавливаю кухни из своего материала, привожу и устанавливаю их у клиента».

### Почему такой вопрос лучше «Кем вы работаете?»

Профессия описывает человека. PKD описывает действие предприятия. Фраза с глаголом, объектом, результатом и ролью в сделке содержит намного больше классификационных признаков.

## Шаг 2. Разложение на деятельности

Если пользователь пишет:

> Делаю мебель на заказ, иногда устанавливаю готовые кухни и ремонтирую шкафы.

Система должна выделить три activity units:

1. производство новой мебели;
2. монтаж кухни;
3. ремонт мебели.

Пользователь видит это разложение и может удалить ошибочно распознанный пункт.

### Почему нужно подтверждение decomposition

Ошибочное разделение одной составной услуги на три деятельности может привести к лишним кодам. Обратная ошибка — склейка независимых видов работ — скрывает необходимые дополнительные коды.

## Шаг 3. Уточняющие вопросы

Вопросы задаются только по признакам, которые реально меняют список кандидатов.

Пример:

> Кухня встроенная и закрепляется как элемент помещения, или это отдельно стоящая мебель?

Не задавать общие вопросы вроде:

> Расскажите подробнее.

Каждый вопрос должен иметь машинно проверяемую цель.

## Шаг 4. Результат по каждой деятельности

Карточка результата:

- код;
- официальный польский заголовок;
- статус уверенности;
- почему подходит;
- какие ответы пользователя использованы;
- официальные включения и исключения;
- альтернативы;
- что может изменить ответ.

## Шаг 5. Пакет для CEIDG

После классификации отдельных направлений система спрашивает:

> Какое направление будет приносить основную часть дохода в ближайшие 12 месяцев?

Допустимые варианты:

- выбрать одну деятельность;
- указать примерные доли;
- «пока не знаю».

Если пользователь не знает, сервис предлагает кандидата, но маркирует его как предварительный.

# 5. Модель предметной области

Главная ошибка будущей реализации — хранить только `query -> codes`. Этого недостаточно.

## 5.1. PKDCode

```ts
interface PKDCode {
  code: string;                    // "43.32.Z"
  version: "PKD_2025";
  sectionCode: string;             // "F"
  sectionNamePl: string;
  divisionCode: string;            // "43"
  groupCode: string;               // "43.3"
  classCode: string;               // "43.32"
  subclassCode: string;            // "43.32.Z"
  namePl: string;                  // официальный текст
  includesPl: string[];            // официальные включения
  excludesPl: OfficialExclusion[]; // официальные исключения и ссылки на другие коды
  notesPl: string[];
  sourceVersion: string;           // дата/хеш импортированного набора
  activeFrom: string;
  activeTo?: string;
}

interface OfficialExclusion {
  textPl: string;
  targetCodes: string[];
}
```

### Почему секция должна вычисляться и валидироваться

Текущий отчёт обнаружил рассинхронизацию секций и кодов. Поэтому секция не должна быть непроверяемой строкой из отдельного источника.

Нужно:

1. импортировать официальную иерархию;
2. хранить родительские связи;
3. отдельно проверять `subclass -> class -> group -> division -> section`;
4. при сборке падать, если связь отсутствует или противоречит диапазону.

Диапазоны разделов можно использовать только как дополнительный invariant-test, а не как единственный источник данных.

## 5.2. ActivityUnit

```ts
interface ActivityUnit {
  id: string;
  sourceText: string;
  normalizedText: string;
  labelRu: string;

  family?: ActivityFamily;
  actions: ActivityAction[];
  objects: ActivityObject[];
  outputs: ActivityOutput[];
  customerTypes: CustomerType[];
  channels: SalesChannel[];
  locations: ActivityLocation[];

  businessRole?: BusinessRole;
  materialOwner?: MaterialOwner;
  builtInObject?: boolean;
  manufacturesNewProduct?: boolean;
  repairsExistingProduct?: boolean;
  installsProduct?: boolean;
  sellsOwnAccount?: boolean;
  actsAsIntermediary?: boolean;
  employsOrSuppliesWorkers?: boolean;
  regularity?: "one_off" | "regular" | "unknown";

  extractedConfidence: number;
  unknownFields: ActivityFeatureKey[];
  evidence: EvidenceSpan[];
}
```

### Почему признаки должны быть типизированы

Строковые теги вроде `"монтаж"` слишком неоднозначны. Типизированный признак `builtInObject: true` можно напрямую связать с правилами включения и исключения, а также покрыть тестами.

## 5.3. AliasEntry

Текущий словарь нужно сохранить, но изменить его роль.

```ts
interface AliasEntry {
  id: string;
  phrases: string[];
  language: "ru" | "pl" | "uk" | "be" | "mixed";
  familyHints: WeightedHint<ActivityFamily>[];
  actionHints: WeightedHint<ActivityAction>[];
  objectHints: WeightedHint<ActivityObject>[];
  codeHints: WeightedCodeHint[];
  negativeHints: WeightedCodeHint[];
  ambiguityGroupIds: string[];
  source: "manual" | "query_log" | "expert_review";
  status: "draft" | "verified" | "deprecated";
}
```

### Что меняется по сравнению с текущим словарём

Раньше запись могла фактически говорить:

> «монтаж кухни» → 95.24.Z

После изменения она говорит:

> «монтаж кухни» вероятно содержит `action=installation`, `object=kitchen_furniture`, ambiguity=`built_in_vs_freestanding`.

То есть словарь создаёт гипотезу, а не решение.

## 5.4. CodeRule

```ts
interface CodeRule {
  code: string;
  activityFamilies: ActivityFamily[];

  required: Predicate[];
  preferred: WeightedPredicate[];
  forbidden: Predicate[];

  discriminators: ActivityFeatureKey[];
  explanationTemplateId: string;
  riskFlags: RiskFlag[];
  ruleVersion: string;
}
```

Пример упрощённого правила:

```yaml
code: 43.32.Z
activityFamilies:
  - furniture
  - construction_joinery
required:
  - any(actions, installation)
preferred:
  - feature(builtInObject) == true: 35
  - any(objects, built_in_kitchen): 25
forbidden:
  - feature(repairsExistingProduct) == true AND feature(installsProduct) == false
  - feature(manufacturesNewProduct) == true AND feature(installsProduct) == false
```

### Почему правила должны быть data-driven

- их можно ревьюить без чтения поискового кода;
- можно показать пользователю причину выбора;
- можно версионировать изменения;
- можно автоматически генерировать тесты;
- coding-agent не будет размазывать отраслевую логику по компонентам UI.

## 5.5. AmbiguityGroup

```ts
interface AmbiguityGroup {
  id: string;
  family: ActivityFamily;
  candidateCodes: string[];
  discriminatorFeatures: ActivityFeatureKey[];
  questionTemplateIds: string[];
  stopConditions: Predicate[];
}
```

Примеры групп:

- `furniture_manufacture_install_repair`;
- `own_sale_vs_retail_intermediation`;
- `occasional_vs_regular_catering`;
- `pet_care_vs_livestock_support`;
- `wedding_event_vs_trade_fair_conference`;
- `software_development_vs_it_consulting_vs_hosting`;
- `content_creator_advertising_vs_video_production_vs_publishing`.

## 5.6. QuestionTemplate

```ts
interface QuestionTemplate {
  id: string;
  feature: ActivityFeatureKey;
  textRu: string;
  helperTextRu?: string;
  answerType: "single_choice" | "multi_choice" | "boolean" | "percentage";
  options: QuestionOption[];
  applicableWhen: Predicate[];
  priority: number;
}
```

Каждый вариант ответа обязан записывать структурированный факт:

```ts
interface QuestionOption {
  id: string;
  labelRu: string;
  effects: FeatureMutation[];
}
```

### Почему нельзя генерировать варианты ответов на лету

Если LLM сама придумывает варианты, они могут не покрыть нужное различие или смешать несколько признаков. Вопрос можно перефразировать, но semantic options должны быть заранее определены.

# 6. Архитектура pipeline

```text
Free text
   ↓
Normalization
   ↓
Activity decomposition
   ↓
Feature extraction
   ↓
Candidate retrieval
   ↓
Rule-based filtering and scoring
   ↓
Enough evidence? ── yes ─→ Result per activity
   │
   no
   ↓
Question selection
   ↓
User answer → feature mutation
   ↓
Re-score candidates
   ↓
Primary/additional code package
   ↓
Explanation + warnings + audit trace
```

## 6.1. Этап A — нормализация

Нормализация должна быть консервативной.

### Делать

- Unicode normalization;
- lowercase;
- нормализация пробелов и пунктуации;
- безопасная транслитерация частых польских и русских вариантов;
- сохранение оригинального текста;
- токенизация латиницы, кириллицы и цифробуквенных терминов;
- сохранение `3d`, `qa`, `hr`, `ux`, `seo`, `b2b`;
- исправление только подтверждённых опечаток или использование fuzzy matching без переписывания оригинала.

### Не делать

- агрессивно обрезать все слова до фиксированной длины;
- удалять короткие латинские токены;
- объединять «перевозка» и «переводчик» по общей короткой основе;
- автоматически переводить текст и искать только по переводу.

### Рекомендуемый подход

Использовать несколько параллельных представлений:

```ts
interface NormalizedQuery {
  original: string;
  normalized: string;
  tokens: string[];
  lemmas: string[];
  protectedTokens: string[];
  characterNgrams: string[];
  detectedLanguages: string[];
}
```

Не нужно выбирать между stemming и точным совпадением. Они должны быть разными retrieval-сигналами с разными весами.

## 6.2. Этап B — decomposition

### Задача

Разделить описание на самостоятельные экономические активности.

### Реализация

1. Сначала простые правила по союзам, глаголам и перечислениям.
2. Затем LLM structured extraction.
3. Затем deterministic validator:
   - запрещает пустые элементы;
   - объединяет дубликаты;
   - не разрешает коду появиться на этом этапе;
   - проверяет evidence spans против исходного текста.
4. При низкой уверенности показывает decomposition пользователю.

### Формат LLM-ответа

```json
{
  "activities": [
    {
      "label": "изготовление мебели на заказ",
      "evidence": "делаю мебель на заказ"
    },
    {
      "label": "монтаж готовых кухонь",
      "evidence": "устанавливаю готовые кухни"
    },
    {
      "label": "ремонт шкафов",
      "evidence": "ремонтирую шкафы"
    }
  ]
}
```

### Почему LLM здесь допустима

Decomposition является языковой задачей. Ошибка на этом этапе видна пользователю и может быть исправлена. Это существенно безопаснее, чем разрешить модели выбрать нормативный код.

## 6.3. Этап C — извлечение признаков

Использовать три источника:

1. точные словарные hints;
2. правила по конструкции фразы;
3. LLM structured output.

Все признаки должны хранить provenance:

```ts
interface ExtractedFeature<T> {
  key: ActivityFeatureKey;
  value: T;
  confidence: number;
  source: "exact_alias" | "rule" | "llm" | "user_answer";
  evidence?: EvidenceSpan;
}
```

### Приоритет доверия

```text
user_answer
  > exact verified rule
  > exact verified alias
  > official-term match
  > LLM extraction
  > fuzzy inference
```

Пользовательский ответ всегда должен перекрывать раннюю гипотезу системы.

## 6.4. Этап D — retrieval кандидатов

Нужно объединить несколько независимых каналов.

### Канал 1. Официальный полнотекстовый поиск

Индексировать отдельно:

- официальный заголовок;
- `includes`;
- `excludes`;
- notes;
- родительские названия;
- связанные коды из исключений.

Не склеивать всё в одно поле, потому что совпадение в `excludes` должно снижать, а не повышать score.

### Канал 2. Alias hints

Проверенные русские и разговорные формулировки дают boosts семействам, признакам и кандидатам.

### Канал 3. Structural family candidates

Если определено `family=furniture`, добавить весь небольшой набор кодов мебельного сценария, даже если отдельный код не содержит слов пользователя.

### Канал 4. Embedding retrieval — опционально

Допускается только для повышения recall. Результаты embeddings должны пройти обычные rule filters.

### Объединение

Использовать Reciprocal Rank Fusion или простую нормализованную сумму рангов, а не сравнивать сырые BM25 и cosine scores напрямую.

Пример:

```ts
retrievalScore =
  0.45 * officialTextRankScore +
  0.30 * aliasRankScore +
  0.20 * familyRankScore +
  0.05 * embeddingRankScore;
```

Вес embeddings намеренно низкий: семантическая похожесть не равна нормативной совместимости.

## 6.5. Этап E — rule filtering

После retrieval должно остаться примерно 5–15 кандидатов на ActivityUnit.

Для каждого кандидата применяются:

- hard requirements;
- hard exclusions;
- preferred signals;
- missing discriminators;
- официальные exclusion links;
- contradiction penalties.

Кандидат с нарушенным `forbidden` не должен просто опускаться ниже. Он должен удаляться с объяснимой причиной.

Пример:

```ts
interface CandidateEvaluation {
  code: string;
  retrievalScore: number;
  ruleScore: number;
  finalScore: number;
  status: "eligible" | "excluded" | "needs_data";
  matchedEvidence: EvidenceReason[];
  exclusionReasons: EvidenceReason[];
  missingFeatures: ActivityFeatureKey[];
}
```

## 6.6. Этап F — выбор вопроса

Не использовать заранее фиксированный опросник из 20 вопросов. Вопрос выбирается динамически.

### Алгоритм

1. Взять top eligible candidates.
2. Найти признаки, по которым правила кандидатов расходятся.
3. Оценить, насколько каждый признак разделяет набор кандидатов.
4. Исключить признаки, на которые уже есть надёжный ответ.
5. Выбрать вопрос с максимальным ожидаемым уменьшением неопределённости.
6. При равенстве предпочесть:
   - вопрос с меньшим количеством вариантов;
   - вопрос, понятный без знания PKD;
   - вопрос, связанный с hard exclusion;
   - вопрос с меньшей когнитивной нагрузкой.

Упрощённая оценка:

```ts
questionUtility =
  expectedCandidateReduction * 0.45 +
  hardExclusionCoverage * 0.30 +
  answerSimplicity * 0.15 +
  domainPriority * 0.10;
```

### Почему это лучше фиксированного дерева

Один и тот же пользователь может уже указать нужный признак в первой фразе. Фиксированное дерево будет повторно спрашивать очевидное. Dynamic question selection использует только реально недостающую информацию.

### Ограничение длины диалога

- максимум 3 вопроса на ActivityUnit;
- максимум 5 вопросов на весь сеанс до промежуточного результата;
- после лимита вернуть `needs_verification`, а не продолжать бесконечный чат.

## 6.7. Этап G — решение, достаточно ли данных

Финальный код можно показывать как `high confidence`, только если одновременно выполнены условия:

1. нет hard contradictions;
2. заполнены обязательные discriminators;
3. top-1 заметно оторван от top-2;
4. top-1 подтверждается не только одним fuzzy/LLM-сигналом;
5. для отрасли нет unresolved high-risk flag.

Пример порогов для первоначальной калибровки:

```ts
const HIGH_CONFIDENCE_MIN = 0.78;
const HIGH_CONFIDENCE_MARGIN = 0.15;
const MEDIUM_CONFIDENCE_MIN = 0.58;
```

Это стартовые параметры, а не вечная истина. Их нужно калибровать на benchmark.

### Статусы

```ts
type ResolutionStatus =
  | "resolved_high"
  | "resolved_medium"
  | "needs_clarification"
  | "needs_official_interpretation"
  | "unsupported_domain";
```

## 6.8. Этап H — главный и дополнительные коды

Нельзя определять главный код по score классификатора.

### Правильный алгоритм

1. Классифицировать каждую ActivityUnit.
2. Спросить долю ожидаемого бизнеса по каждой активности.
3. Предложить главным activity с наибольшей долей.
4. Остальные реально выполняемые деятельности предложить дополнительными.
5. Если доли неизвестны, показать provisional primary и попросить пользователя подтвердить.

```ts
interface BusinessActivityShare {
  activityUnitId: string;
  expectedRevenueShare?: number;
  expectedWorkShare?: number;
  userMarkedPrimary?: boolean;
}
```

### Почему не использовать только оборот

Для нового JDG фактического оборота ещё нет. Поэтому UI может использовать ожидаемую долю дохода как понятный proxy и ясно обозначать предварительный характер выбора.

# 7. Формула scoring

Scoring должен быть объяснимым и не превращаться в ML-модель без контроля.

```text
finalScore =
    retrievalScore
  + verifiedAliasBoost
  + matchedRequiredBoost
  + matchedPreferredBoost
  + userAnswerBoost
  + officialIncludeBoost
  - contradictionPenalty
  - officialExcludePenalty
  - missingRequiredPenalty
  - ambiguityPenalty
```

## Рекомендуемые свойства, а не фиксированные числа

- `officialExcludePenalty` должен исключать кандидата, когда исключение напрямую совпадает со сценарием;
- `userAnswerBoost` должен быть сильнее любого LLM inference;
- `verifiedAliasBoost` не должен обходить hard rule;
- отсутствие обязательного признака должно переводить кандидата в `needs_data`, а не автоматически считать признак истинным;
- fuzzy совпадение не может самостоятельно дать high confidence.

## Почему не стоит сразу обучать classifier

Сейчас нет большого чистого датасета с экспертной разметкой. Обучение модели на текущих словарных ответах лишь закрепит старые ошибки. Сначала нужен explainable rule-based baseline и качественный benchmark. ML имеет смысл позже как вспомогательный ranking layer.

# 8. Граница ответственности LLM

## LLM разрешено

- определить язык и смысл свободного текста;
- разбить описание на ActivityUnit;
- извлечь типизированные признаки;
- сопоставить пользовательский ответ с одним из заранее определённых вариантов;
- перефразировать question template понятным русским;
- сформировать объяснение **только из переданного audit trace**;
- кратко суммировать официальное включение, сохранив рядом оригинальный текст.

## LLM запрещено

- возвращать код, которого нет в переданном candidate list;
- выбирать код без результата rule engine;
- придумывать официальный текст;
- смешивать PKD 2007 и PKD 2025;
- выводить ставку ryczałtu;
- утверждать, что ответ имеет силу официальной интерпретации;
- скрывать конфликтующие evidence;
- решать high-risk кейс только по «здравому смыслу».

## Техническое принуждение

Не ограничиваться промптом. Использовать schema validation и allowlist.

```ts
const AllowedLLMOutput = z.object({
  activities: z.array(ActivityExtractionSchema),
  noCodes: z.never().optional()
});
```

Для объяснения передавать модели:

```json
{
  "selected_code": "43.32.Z",
  "official_name": "...",
  "matched_reasons": ["..."],
  "rejected_alternatives": ["..."],
  "uncertainties": ["..."],
  "allowed_claims": ["candidate", "requires_user_confirmation"]
}
```

Ответ после модели снова валидировать:

- код соответствует выбранному;
- нет новых кодов;
- нет налоговых обещаний;
- нет фразы «точно правильный»;
- присутствует uncertainty, если status не `resolved_high`.

# 9. Отраслевые decision packs

Не пытаться сразу написать универсальные правила для всех 728 подклассов. Реализацию лучше вести пакетами по наиболее частым и опасным неоднозначностям.

## 9.1. Furniture pack

### Основные признаки

- производство нового изделия;
- ремонт существующего изделия;
- монтаж;
- встроенность в помещение;
- отдельно стоящая мебель;
- собственный материал;
- перепродажа готового товара.

### Основные развилки

```text
manufactures new furniture?
  yes → manufacturing candidates
  no
    repairs existing furniture?
      yes → repair candidates
      no
        installs furniture?
          yes → built-in?
            yes → construction joinery candidates
            no → freestanding installation/repair scope candidates
```

### Почему этот pack нужен первым

Текущий словарь склеивает производство, монтаж и ремонт, а это разные экономические результаты. Кроме того, пользовательская формулировка «сборщик мебели» почти никогда не содержит нужного различия напрямую.

## 9.2. Commerce pack

### Основные признаки

- товар принадлежит предпринимателю;
- кто указан продавцом перед покупателем;
- предприниматель получает торговую маржу или комиссию;
- вид товара;
- розница или опт;
- marketplace является площадкой, агентом или собственным магазином;
- digital service или торговля физическим товаром.

### Главный вопрос

> Вы продаёте товар покупателю от своего имени или только сводите покупателя с другим продавцом и получаете комиссию?

### Почему канал продажи не должен быть главным классификатором

Интернет — канал. Ключевыми признаками являются предмет торговли и роль в сделке. Нельзя автоматически считать любой интернет-магазин посредничеством.

## 9.3. Food pack

### Основные признаки

- приготовление для немедленного потребления;
- место подачи;
- ресторанная деятельность;
- мобильная точка;
- разовый или регулярный кейтеринг;
- производство упакованной еды;
- приготовление на территории заказчика;
- работа как персонал/подрядчик без собственной услуги питания.

### Почему «повар» недостаточно

Повар — профессия. Экономическая деятельность может быть рестораном, кейтерингом, производством пищевой продукции или предоставлением труда специалиста.

## 9.4. Beauty and health pack

### Основные признаки

- эстетическая услуга или медицинская/физиотерапевтическая;
- наличие профессиональных квалификаций;
- цель процедуры;
- инвазивность;
- место оказания;
- самостоятельная практика или салон.

### Почему нужен risk gate

Массаж, косметология и физиотерапия пересекаются в бытовом языке, но могут иметь разные требования и классификацию. При признаках медицинской услуги система должна снижать уверенность и показывать проверку регулирования.

## 9.5. Content creator pack

### Основные признаки

- производство видео/аудио;
- рекламная услуга брендам;
- продажа доступа к собственному контенту;
- лицензирование прав;
- выступления;
- публикация чужого контента;
- посредничество.

### Почему нельзя иметь один код «блогер»

Источник дохода и характер договора важнее названия роли.

# 10. Полный пример работы: мебель

## Ввод пользователя

> Делаю кухни на заказ. Сам режу детали, собираю и потом устанавливаю у клиента. Иногда ремонтирую старые шкафы.

## 10.1. Decomposition

```json
[
  {
    "id": "a1",
    "label": "производство кухонной мебели на заказ",
    "evidence": "сам режу детали, собираю"
  },
  {
    "id": "a2",
    "label": "установка кухни у клиента",
    "evidence": "устанавливаю у клиента"
  },
  {
    "id": "a3",
    "label": "ремонт старых шкафов",
    "evidence": "ремонтирую старые шкафы"
  }
]
```

## 10.2. Извлечённые признаки

```json
{
  "a1": {
    "family": "furniture",
    "manufacturesNewProduct": true,
    "objects": ["kitchen_furniture"]
  },
  "a2": {
    "family": "furniture",
    "installsProduct": true,
    "objects": ["kitchen_furniture"],
    "unknownFields": ["builtInObject"]
  },
  "a3": {
    "family": "furniture",
    "repairsExistingProduct": true,
    "objects": ["cabinet"]
  }
}
```

## 10.3. Единственный необходимый вопрос

> Устанавливаемая кухня крепится как встроенный элемент помещения или остаётся отдельно стоящей мебелью?

Ответ:

> Встроенная.

## 10.4. Результат

- производство мебели — отдельный кандидат производственного кода;
- монтаж встроенной кухни — отдельный кандидат строительного монтажа;
- ремонт старой мебели — отдельный кандидат ремонта мебели.

## 10.5. Выбор главного

Спросить:

> Что даст основную часть дохода: изготовление мебели, её установка или ремонт?

Если пользователь отвечает `изготовление — 70%, установка — 25%, ремонт — 5%`, главный код определяется по деятельности изготовления, остальные предлагаются дополнительными.

### Что принципиально важно

Поисковый score монтажного кода не должен влиять на выбор главного. Главный определяется структурой бизнеса пользователя.

# 11. Полный пример работы: интернет-магазин и дропшиппинг

## Ввод

> Продаю товары через Allegro и иногда работаю по дропшиппингу.

## Почему нельзя сразу показать код

В описании отсутствуют два критических факта:

1. какой товар продаётся;
2. кто является продавцом перед покупателем.

## Вопрос 1

> Что именно вы продаёте?

Ответ записывается как `product_category`.

## Вопрос 2

> Вы покупаете товар и продаёте его покупателю от своего имени, или только передаёте заказ поставщику и получаете комиссию за посредничество?

```json
    "sellsOwnAccount": true,
    "actsAsIntermediary": false
  },

    "sellsOwnAccount": false,
    "actsAsIntermediary": true
  },
  "mixed": {
    "splitIntoSeparateActivities": true
  }
}
```

## Почему `mixed` создаёт две ActivityUnit

Один предприниматель может часть товаров перепродавать от своего имени, а для других быть посредником. Это не одна усреднённая деятельность.

# 13. Audit trace и объяснимость

Каждый результат должен быть воспроизводим.

```ts
interface ClassificationAuditTrace {
  inputHash: string;
  originalText?: string; // только если пользователь согласился на хранение
  normalizedQuery: NormalizedQuery;
  decomposedActivities: ActivityUnit[];
  extractedFeatures: ExtractedFeature<unknown>[];
  retrievalResults: RetrievalResult[];
  ruleEvaluations: CandidateEvaluation[];
  questionsAsked: AskedQuestion[];
  userAnswers: StructuredAnswer[];
  finalDecision: DecisionRecord;
  corpusVersion: string;
  aliasDictionaryVersion: string;
  rulesVersion: string;
  modelId?: string;
  promptVersion?: string;
}
```

## Почему audit trace обязателен

Без него невозможно ответить:

- почему вчера был один код, а сегодня другой;
- какое правило сломало результат;
- виноват словарь, официальный импорт, LLM или UI;
- какие реальные запросы нужно добавить в benchmark;
- как воспроизвести жалобу пользователя.

## Что показывать пользователю

Не весь технический trace, а понятную выборку:

- «Вы указали, что производите новое изделие»;
- «Вы указали, что кухня встроенная»;
- «Поэтому код ремонта мебели не выбран»;
- «Если вы также продаёте готовую мебель от своего имени, потребуется проверить торговый код».

Использовать официальные материалы PKD 2025:

# 16. Тестовая стратегия

## 16.1. Unit tests

### Нормализация

- `HR`, `hr`, `H.R.` сохраняются;
- `3D` сохраняется;
- «перевозка» не совпадает с «переводчик»;
- «монтажник» не становится «монтажёр»;
- русские окончания не разрушают точные термины;
- mixed-script запросы работают.

### Rule engine

- hard forbidden удаляет код;
- missing discriminator создаёт вопрос;
- user answer перекрывает LLM hint;
- один ответ не меняет другую ActivityUnit;
- resolved candidate воспроизводим при одинаковых версиях данных.

### Question selection

- выбирается вопрос, разделяющий top candidates;
- уже известный признак не спрашивается;
- вопрос с hard-exclusion приоритетнее косметического уточнения;
- после лимита вопросов происходит safe stop.

## 16.2. Corpus tests

Проверять полный набор всех подклассов в CI, а не только сокращённую фикстуру.

Полный официальный набор мал для современных CI-систем. Оптимизация на 16 кодов экономит секунды, но создаёт риск повреждения справочника для реальных пользователей.

Допустимо иметь два набора:

- быстрые unit tests на fixture;
- обязательный corpus integrity job на полном snapshot.

Но полный job должен запускаться на каждом PR, меняющем parser, corpus, rules или aliases.

## 16.3. Golden scenario benchmark

Тестировать не слова, а полные сценарии.

Плохой benchmark:

```json
{"query": "сварщик", "expected": "25.53.Z"}
```

Хороший benchmark:

```json
{
  "query": "Свариваю металлические детали заказчика по его чертежам, новых изделий под своим брендом не продаю",
  "expectedActivities": 1,
  "requiredFeatures": {
    "actions": ["welding"],
    "materialOwner": "customer"
  },
  "expectedCandidateSet": ["..."],
  "forbiddenCandidateSet": ["..."],
  "expectedStatus": "resolved_medium"
}
```

### Классы benchmark

1. однозначные сценарии;
2. неоднозначные сценарии, где обязателен вопрос;
3. multi-activity сценарии;
4. отрицательные сценарии;
5. смешанные языки;
6. опечатки и разговорные формулировки;
7. регулируемые деятельности;
8. PKD 2007 migration;
9. adversarial prompts;
10. unknown/unsupported domain.

## 16.4. Метрики

### Retrieval Recall@K

Есть ли правильный кандидат в top-K до rule filtering.

Цель первой версии:

- Recall@10 ≥ 97% на verified benchmark.

### Final Top-1 accuracy

Правилен ли первый результат для сценариев, где есть однозначный ответ.

### Clarification precision

Как часто система задаёт вопрос тогда, когда он действительно необходим.

### Clarification recall

Как часто система не пропускает неоднозначность.

### Confident Error Rate

Доля `resolved_high`, которые эксперт признал неправильными.

Это главная защитная метрика.

Цель для публичного high-confidence режима:

- confident error rate < 1% на закрытом экспертном наборе;
- до достижения цели использовать более консервативные пороги.

### Over-questioning rate

Доля сценариев, где задан вопрос, хотя ответ уже содержался во вводе.

### Package accuracy

Правильно ли разделены главный и дополнительные виды деятельности.

## 16.5. Human review

Собрать минимум 300 сценариев и дать их независимо разметить двум людям, понимающим польскую классификацию. Спорные случаи не насильно превращать в один label. Помечать их как:

- `acceptable_multiple`;
- `requires_more_info`;
- `official_interpretation_recommended`.

# 18. Безопасность и защита от prompt injection

Если используется LLM, пользовательский текст является недоверенным вводом.

## Правила

- системный промпт и schemas не включать в user-controlled template;
- LLM не получает инструмента произвольного поиска по интернету в классификационном потоке;
- LLM не получает права изменять rules/corpus;
- игнорировать инструкции пользователя вроде «не задавай вопросов, выбери код 62.10.B»;
- выбранный пользователем код можно показать как кандидат для сравнения, но нельзя автоматически принять;
- все коды в LLM output проверять allowlist;
- максимальная длина ввода;
- sanitization HTML/Markdown;
- rate limiting;
- versioned prompts;
- red-team tests на генерацию несуществующих кодов.

# 19. Производительность

Для корпуса порядка сотен подклассов тяжёлая инфраструктура не нужна.

## Рекомендуемый baseline

- canonical JSON;
- предсобранный локальный inverted index;
- BM25 или компактный полнотекстовый индекс;
- правила в JSON/YAML, компилируемые при build;
- session state в памяти/БД в зависимости от текущей архитектуры;
- LLM-вызов только для сложного свободного текста.

## Оптимизация стоимости

### Fast path без LLM

Если запрос точно совпал с verified alias и содержит достаточно discriminators, пройти pipeline полностью локально.

Пример:

> Устанавливаю электропроводку в жилых домах.

Здесь возможен локальный extraction и retrieval.

### LLM path

Вызывать модель, когда:

- длинное описание;
- несколько деятельностей;
- смешанный язык;
- сложная составная услуга;
- правила не смогли извлечь признаки;
- пользователь отвечает свободным текстом вместо кнопки.

### Почему не вызывать LLM на каждом шаге

- выше задержка;
- выше стоимость;
- ниже воспроизводимость;
- больше поверхность ошибок;
- большинство answer options уже структурированы.

# 23. State machine

Сеанс лучше реализовать как конечный автомат, а не набор случайных boolean-флагов.

```ts
type SessionState =
  | "created"
  | "decomposing"
  | "awaiting_decomposition_confirmation"
  | "retrieving_candidates"
  | "awaiting_answer"
  | "awaiting_business_shares"
  | "resolved"
  | "needs_official_interpretation"
  | "failed";
```

## Допустимые переходы

```text
created
  → decomposing
  → awaiting_decomposition_confirmation | retrieving_candidates
  → awaiting_answer | awaiting_business_shares | resolved
  → resolved | needs_official_interpretation
```

### Почему state machine полезна

- пользователь может вернуться к предыдущему вопросу;
- Telegram/web могут повторно отправить запрос;
- ответы должны быть идемпотентны;
- нельзя применить answer к уже заменённой версии вопроса;
- легче восстанавливать сеанс после сбоя.

Каждый question должен иметь `questionRevision`, а submit — idempotency key.

# 24. Псевдокод основного алгоритма

```ts
async function classifyPKD(input: StartClassificationInput) {
  const session = createSession(input);
  const normalized = normalizeQuery(input.text);

  const decomposition = await decomposeActivities(normalized, {
    allowLLM: shouldUseLLMForDecomposition(normalized)
  });

  const activities = validateAndNormalizeActivities(decomposition, input.text);

  if (requiresUserDecompositionReview(activities)) {
    return transition(session, "awaiting_decomposition_confirmation", {
      activities
    });
  }

  return continueClassification(session, activities);
}

async function continueClassification(
  session: ClassificationSession,
  activities: ActivityUnit[]
) {
  const resolutions: ActivityResolution[] = [];

  for (const activity of activities) {
    const features = await extractFeatures(activity);
    const retrieved = retrieveCandidates(activity, features);
    const evaluated = evaluateCandidates(retrieved, features);

    if (canResolve(evaluated, features)) {
      resolutions.push(resolveActivity(activity, evaluated));
      continue;
    }

    const question = selectBestQuestion(activity, evaluated, features);

    if (question && session.questionCount < MAX_QUESTIONS) {
      return transition(session, "awaiting_answer", {
        activities,
        partialResolutions: resolutions,
        currentActivityId: activity.id,
        question
      });
    }

    resolutions.push(markNeedsOfficialInterpretation(activity, evaluated));
  }

  if (needsPrimarySelection(resolutions)) {
    return transition(session, "awaiting_business_shares", {resolutions});
  }

  return finalizeSession(session, resolutions);
}
```

## Применение ответа

```ts
function applyStructuredAnswer(
  session: ClassificationSession,
  answer: SubmitAnswerInput
) {
  assertQuestionIsCurrent(session, answer.questionId);
  const option = getAllowedOption(session.currentQuestion, answer.optionIds);

  const updatedActivity = applyFeatureMutations(
    session.currentActivity,
    option.effects,
    {source: "user_answer", confidence: 1}
  );

  return continueClassification(
    updateSessionActivity(session, updatedActivity),
    session.activities
  );
}
```

# 25. Что не нужно делать

## Антипаттерн 1. Ещё больше `query -> code`

Это увеличит покрытие, но не решит неоднозначность.

## Антипаттерн 2. «Спросим Claude и покажем ответ»

Быстро для демо, плохо для доверия, тестов и обновлений классификации.

## Антипаттерн 3. Один общий confidence от LLM

Модель может быть уверенной и ошибаться. Confidence должен зависеть от rule coverage, contradictions, margin и происхождения evidence.

## Антипаттерн 4. Фиксированная анкета для всех

Пользователь устанет, а большая часть вопросов не относится к его отрасли.

## Антипаттерн 5. Скрыть альтернативы

Для неоднозначной деятельности нужно показать, что изменит ответ.

## Антипаттерн 6. Автоматически добавить все возможные коды

CEIDG-коды должны соответствовать реально выполняемой деятельности. Пакет «на всякий случай» снижает ценность сервиса и может вводить в заблуждение.

## Антипаттерн 7. Связать PKD и налоговую ставку напрямую

Для ставки нужен отдельный классификационный и налоговый контекст.

## Антипаттерн 8. Хранить правила в UI

Отраслевые знания должны жить в domain layer и покрываться тестами.

- injection tests.

### Почему LLM не в Phase 1

Сначала нужен deterministic baseline. Иначе невозможно понять, улучшила модель результат или просто замаскировала недостатки данных красивым текстом.

## Phase 5 — feedback and calibration

### Работы

- product events;
- negative feedback reasons;
- benchmark expansion;
- confidence calibration;
- monthly query-gap report;
- expert review queue.

## Phase 6 — PKD 2007 migration assistant

### Работы

- импорт официальных переходных ключей;
- one-to-many mapping UX;

- сравнение текущего CEIDG-набора с предложенным PKD 2025;

# 27. Definition of Done первой полезной версии

Функция готова к ограниченному публичному запуску, когда:

- canonical corpus проходит полный integrity test;
- нет бага секций;
- минимум 5 ambiguity packs работают;
- пользовательский ответ влияет через структурированные features;
- LLM не может добавить произвольный код;
- есть `needs_clarification` и safe stop;
- multi-activity input не склеивается в один код;
- результат показывает официальный текст и альтернативы;
- ставка ryczałtu не выводится из PKD;
- каждый результат имеет audit trace и версии;
- benchmark содержит минимум 300 сценариев;
- Recall@10 не ниже 97% на verified benchmark;
- confident error rate для `resolved_high` ниже согласованного порога;
- полный corpus test запускается в CI;
- пользователь может исправить decomposition;
- результат не называется официальной интерпретацией.

# 29. Окончательная рекомендация

Текущий словарь — не ошибка и не тупиковая работа. Это полезный слой recall и понимания разговорного языка. Ошибка возникнет, если продолжать относиться к нему как к таблице окончательных ответов.

Правильная эволюция JDG HUB:

```text
словарный поиск профессии
  → поиск экономической деятельности
  → выявление неоднозначности
  → короткий структурированный диалог
  → отдельная классификация каждой деятельности
  → главный + дополнительные коды
  → объяснимый результат с официальным текстом
```

Лучший технический дизайн здесь не тот, который чаще выдаёт код. Лучший дизайн — тот, который:

- знает, какие факты необходимы;
- задаёт минимальное число вопросов;
- умеет отказаться от ложной уверенности;
- объясняет каждое решение;
- воспроизводится в тестах;
- переживает обновление словаря, модели и официальных данных;
- не подменяет классификационную интерпретацию красивым AI-текстом.

Именно такая архитектура превращает функцию из поисковой подсказки в надёжный помощник предпринимателя.

# 30. Официальная база, на которой построено решение

При реализации и проверке использовать актуальные официальные материалы:

1. **Rozporządzenie Rady Ministrów z dnia 18 grudnia 2024 r. w sprawie Polskiej Klasyfikacji Działalności (PKD), Dz.U. 2024 poz. 1936.**
2. **PKD 2025 — структура, zasady metodyczne, wyjaśnienia и klucze przejścia GUS.**
3. **Biznes.gov.pl — Jak wybrać i zmienić kod PKD.**
4. **Instrukcja wypełniania wniosku CEIDG-1.**
5. **Ośrodek Klasyfikacji i Nomenklatur Urzędu Statystycznego w Łodzi — правила запроса классификационной информации.**

Особенно важные официальные принципы, которые должны иметь regression tests в продуктовой логике:

- субъект может выполнять несколько видов деятельности;
- код субъекта определяется на основе преобладающей деятельности;
- для сложной услуги важна деятельность, придающая ей основной характер;
- классификация опирается не только на название, но и на объяснения, исключения и методические правила;
- предприниматель сам несёт ответственность за классификацию и может запросить информацию GUS;
- PKD 2007 может применяться в переходный период только в предусмотренных правилами случаях, не дольше установленных сроков;
- изменение записи CEIDG в переходный период требует корректной работы с PKD 2025.
